# ADR-0005. Структура проекта

- **Статус:** принято
- **Дата:** 2026-08-25

## Контекст

`django-admin startproject` создаёт плоскую раскладку: пакет настроек и
приложения лежат в корне вперемешку с `Dockerfile`, `pyproject.toml` и прочей
инфраструктурой. Для учебного проекта это нормально, для продукта, который
собирают в образ и деплоят, — нет: непонятно, где проходит граница «что
деплоим».

[ADR-0004](0004-application-architecture.md) задал слои ответственности. Этот
документ кладёт их на файлы и каталоги.

## Решение

### Раскладка репозитория

Весь Python-код живёт в `src/`, корень остаётся под конфигурацию и инфраструктуру.

```
GymOps/
├── .github/workflows/
├── docs/
├── media/                    ← данные времени выполнения, вне src/
├── src/
│   ├── config/               ← настройки, urls, wsgi, asgi
│   │   └── settings/
│   ├── apps/                 ← доменные приложения
│   ├── templates/
│   └── static/
├── compose.yaml
├── Dockerfile
├── pyproject.toml
├── uv.lock
├── .env.example
└── manage.py
```

Границы простые: **корень — конфигурация, `src/` — код, `media/` — данные.**

Следствия, ради которых это делается: инструменты (линтер, проверка типов)
нацелены на один каталог; Dockerfile копирует `src/` как единый артефакт; при
чтении репозитория сразу видно, что относится к продукту, а что к его сборке.

### `media/` находится вне `src/`

Загруженные пользователями файлы — не исходный код. Внутри `src/` они нарушали
бы собственный принцип раскладки и попадали бы в образ, тогда как в проде media
живёт на отдельном томе или во внешнем хранилище.

`static/` остаётся внутри `src/`: исходные стили и скрипты — часть кода. Каталог
собранной статики генерируется при сборке и в репозиторий не попадает.

### Путь импорта задаётся декларативно

`src/` попадает в пути поиска модулей **через конфигурацию окружения**, а не
через изменение `sys.path` в коде: переменная окружения в Docker и compose,
настройка pytest в `pyproject.toml`, соответствующий рабочий каталог у
сервера приложений.

Причина: правило должно быть одно и лежать в одном месте. Мутация `sys.path`
внутри `manage.py` работает только для тех, кто входит через `manage.py`, —
каждый следующий вход (тесты, сервер приложений, фоновый воркер, разовый скрипт,
автодополнение в IDE) приходится чинить отдельно.

Импорты при этом остаются чистыми: `from apps.clients.models import Client`.

### Настройки — пакет с разделением по окружениям

```
src/config/settings/
├── base.py          ← общее
├── local.py         ← разработка
├── production.py    ← прод
└── test.py          ← тесты
```

**Значения** при этом читаются из переменных окружения. Это не противопоставление
подходов: файлы задают *структуру* и отличия окружений, окружение поставляет
*значения* и секреты.

Критерий, по которому выбрано разделение: различия между локалкой и продом должны
быть **видимыми и проверяемыми на ревью**. В едином файле с ветвлениями по флагу
они растворяются в условиях, и ошибка конфигурации обнаруживается на проде.

### Структура приложения

Файлы соответствуют слоям из ADR-0004:

```
src/apps/<приложение>/
├── models.py         ← данные и инварианты
├── managers.py       ← переиспользуемые выборки
├── services.py       ← операции, меняющие состояние; транзакции здесь
├── selectors.py      ← сложные запросы на чтение
├── forms.py          ← валидация формата
├── views.py          ← разобрать запрос → вызвать сервис → ответ
├── admin.py
├── urls.py
├── apps.py
├── migrations/
└── tests/
    ├── test_models.py
    ├── test_services.py
    └── test_views.py
```

Модуль превращается в пакет (`services/`), когда файл разрастётся, — не раньше.

**Селекторы возвращают `QuerySet`, а не список.** Это не деталь оформления:
ленивый QuerySet позволяет вызывающему коду добавить пагинацию, сортировку и
подгрузку связанных объектов, собрав всё в один запрос. Селектор задаёт правило
выборки, а не готовый результат.

### Тесты живут внутри приложения

Тесты лежат рядом с кодом, который проверяют. Приложение остаётся
самодостаточным: его можно прочитать, перенести или удалить целиком.

### Общий код заранее не заводится

Каталог для общего кода (базовые абстрактные модели, миксины, middleware)
появляется **в момент, когда одно и то же понадобилось во втором приложении**, и
называется по своему содержимому.

Имя `core` не используется: оно ничего не сообщает и притягивает всё, для чего
не нашлось места. Общее нельзя спроектировать заранее — его можно только
обнаружить.

## Открытый вопрос: границы приложений

Решение отложено до этапа 2 сознательно. Провести границы между приложениями, не
имея моделей, — это гадание: границы определяются связями, а связей ещё нет.

**Критерий, который применяется в этапе 2.** Приложение — это единица
переиспользования, замены и удаления, а не папка для складывания похожего.

Разделять, когда:
- модели меняются по разным причинам и в разное время
- можно осмысленно представить удаление одного без другого
- у частей разные внешние интерфейсы или разные потребители

Не разделять, когда:
- модели всегда меняются вместе
- между ними плотные связи и общие транзакции
- граница проходит по «похожести», а не по причине изменения

Конкретный вопрос, который предстоит решить: являются ли абонементы и посещения
одним приложением или двумя, если посещение списывается с абонемента внутри
одной транзакции.

## Последствия

- Отклонение от стандартной раскладки Django требует пояснения в README: где
  лежит код, как задан путь импорта, откуда запускается сервер
- Примеры из документации Django и большинства руководств предполагают плоскую
  структуру — их придётся мысленно транслировать
- Создание приложения через штатную команду потребует указывать корректный путь
  и имя (`apps.<имя>`), либо собственного шаблона приложения
- Разделение настроек требует явного указания нужного модуля при каждом запуске:
  в compose, в Dockerfile, в CI, в конфигурации тестов

## Рассмотренные альтернативы

**Плоская структура из `startproject`.** Привычна, не требует пояснений, все
примеры работают как есть. Отвергнута: код и инфраструктура перемешаны, нет
чёткой границы артефакта деплоя.

**`backend/` вместо `src/`.** Отвергнуто: имя обещает соседний `frontend/`,
которого не будет — клиентская часть рендерится сервером, а мобильное приложение
будет отдельным репозиторием.

**`app/` вместо `src/`.** Отвергнуто: слово «app» в Django уже занято и означает
Django-приложение. Раскладка вида `app/apps/clients` читается плохо.

**Пакет проекта как корень кода (`gymops/`).** Отвергнуто: конфликтует с
конвенцией, по которой этим именем называют пакет настроек.

**Единый `settings.py` со значениями из окружения.** Меньше файлов, соответствует
подходу «вся конфигурация в окружении». Отвергнут: отличия окружений становятся
невидимыми, растворяясь в ветвлениях по флагам.

**Тесты отдельным деревом в корне.** Отвергнуто: приложение перестаёт быть
самодостаточным, а путь до теста перестаёт соответствовать пути до кода.
