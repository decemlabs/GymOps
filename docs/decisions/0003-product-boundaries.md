# ADR-0003. Границы продукта

- **Статус:** принято
- **Дата:** 2026-08-25

## Контекст

Discovery по домену фитнес-клуба вскрыл заметно больше, чем разумно строить:
корпоративные клиенты, филиалы, интеграции с кассой и бухгалтерией, мобильное
приложение, AI-ассистент. Без явно проведённых границ невозможно отличить
«отложено» от «не будет никогда», а значит невозможно решить, что закладывать в
фундамент, а что можно спокойно проигнорировать.

Три вопроса требовали ответа до начала кода, потому что каждый из них меняет
архитектуру, а не только объём работ.

## Решение

### Целевой продукт — сеть клубов одного владельца

Система рассчитана на одну организацию с несколькими филиалами: общая клиентская
база, сводная отчётность, единое управление.

На старте филиал ровно один, но **сущность «Клуб» заводится с первого дня**.
Добавлять привязку к филиалу задним числом — значит менять почти все таблицы и
все запросы, причём пропущенный фильтр не падает с ошибкой, а тихо показывает
чужие данные.

### SaaS для независимых клубов — отрезан насовсем

Система не будет предоставляться по подписке нескольким независимым
клубам-конкурентам.

Это самое ценное из трёх решений, потому что оно **снимает требование**, а не
добавляет его: не нужна жёсткая изоляция данных между организациями, при которой
одна забытая проверка в коде приводит к утечке данных конкуренту. Не нужны
подписки, тарифы платформы, биллинг арендаторов и самостоятельная регистрация
организаций.

Формально сеть филиалов и SaaS выглядят похоже — и там, и там данные разделены.
Разница в цене ошибки: внутри одной сети случайно показанные данные соседнего
филиала — недоразумение, между конкурентами — потеря клиента и репутации.
Требование, которое нельзя нарушить ни при какой ошибке в коде, стоит на порядок
дороже требования «обычно фильтруем правильно».

### Клиентский канал и API — входят в продукт

Личный кабинет, онлайн-запись, онлайн-оплата и REST API как основа мобильного
приложения — часть целевого продукта, релиз v0.5.

## Последствия

- **Бизнес-логика не может жить во вьюхах.** У системы будет второй интерфейс
  (API) поверх той же логики. Логика, написанная внутри вьюх, окажется
  продублированной, и две копии разойдутся. Из этого следует [ADR-0004](0004-application-architecture.md),
  и слои вводятся с первого приложения, а не в v0.5
- **Клиент отделён от учётной записи.** Большинство клиентов никогда не входит в
  систему, но у части появится личный кабинет. Учётная запись должна привязываться
  к существующей карточке клиента, а не создавать вторую сущность
- **Идентификаторы уходят наружу** — в API, в QR-коды, на клиентские карты.
  Это влияет на выбор типа первичного ключа, который делается в v0.1
- **Привязка к клубу закладывается в схему сразу**, хотя используется только в v0.8
- **Изоляция данных не является требованием безопасности.** Разделение по
  филиалам решается обычной фильтрацией, без отдельного слоя защиты

## Рассмотренные альтернативы

**Один клуб без возможности расширения.** Проще всего: никакой привязки к
филиалу, никаких лишних сущностей. Отвергнут: сеть входит в планы владельца, и
цена дооснащения позже несопоставима с ценой одной таблицы сейчас.

**SaaS для независимых клубов.** Более амбициозный продукт с потенциально
большим рынком. Отвергнут: добавляет целый слой требований (гарантированная
изоляция, биллинг подписок, самостоятельный онбординг), каждое из которых
конкурирует за время с основной целью — освоением Django через реальный домен.
Решение окончательное; если когда-нибудь понадобится, это будет другой продукт,
а не расширение этого.

**Внутренняя система без клиентского канала.** Клиент взаимодействует только
через администратора и турникет. Отвергнут: онлайн-запись и онлайн-оплата — то,
без чего современный клуб не конкурирует, и отсутствие API обеднило бы проект как
учебный материал.
