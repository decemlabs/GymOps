# ADR-0001. Технологический стек

- **Статус:** принято
- **Дата:** 2026-08-25

## Контекст

Проект начинается с нуля. Версии нужно зафиксировать **до** установки чего-либо:
они определяют совместимость компонентов между собой и воспроизводимость
окружения на машине разработчика, в CI и на проде.

Проект ведётся как коммерческий и рассчитан на поддержку в течение лет. Поэтому
важен не только текущий выбор, но и понимание, когда и какой ценой придётся
обновляться. Отдельное требование — учебное: проект существует в том числе для
глубокого освоения Django, и это влияет на выбор между «стабильно» и «актуально».

## Решение

### Django 6.1

Последний стабильный релиз. Поддерживает Python 3.12–3.14.

Выбран вместо LTS сознательно. Основной аргумент — учебная цель: изучать
фреймворк имеет смысл на актуальном API, а не на замороженном два года назад.
Дополнительный аргумент — путь обновления короткий: следующий LTS выходит в
пределах той же мажорной версии, то есть переход на него будет небольшим шагом,
а не миграцией через несколько релизов.

### Python 3.14

Уже установлен локально, входит в диапазон, поддерживаемый Django 6.1.
Отдельного решения не потребовал — версия продиктована совместимостью.

### PostgreSQL 17

Реляционная СУБД обязательна: домен транзакционный. Списание посещения с
абонемента, продажа, будущая конкурентная запись на занятия — всё это требует
настоящих транзакций, ограничений целостности на уровне базы и предсказуемого
поведения при параллельном доступе.

Версия 17 — зрелый релиз, поддерживаемый Django 6.1. Фиксируется явно
(`postgres:17` в docker-compose), а не через `latest`: смена мажорной версии
делает существующий каталог данных несовместимым, и база просто не поднимется.

### psycopg 3

Актуальная линейка драйвера PostgreSQL для Python. Вторая линейка находится в
режиме поддержки, развитие идёт в третьей. Поддерживается Django с версии 4.2.

Даёт нативную асинхронность, серверную привязку параметров запроса и встроенный
пул соединений — всё это понадобится по мере роста проекта.

### uv

Менеджер окружений и зависимостей.

Ключевой критерий выбора — **воспроизводимость**: uv ведёт lock-файл, который
фиксирует точные версии всех пакетов, включая транзитивные. Это гарантирует, что
на машине разработчика, в CI и на проде встанет одно и то же. Обычный список
зависимостей такой гарантии не даёт: одна и та же строка `django>=6.1` завтра
поставит другую версию.

Дополнительно uv заменяет собой связку из нескольких инструментов (создание
виртуального окружения, установка пакетов, управление версиями Python) и
работает заметно быстрее аналогов.

## Последствия

- **Поддержка Django 6.1 конечна.** Основная поддержка — до выхода следующего
  релиза, затем только исправления безопасности. Обновление на ближайший LTS
  должно быть запланировано, а не встречено внезапно
- **Свежесть стека имеет цену.** На последнем Django и последнем Python часть
  сторонних библиотек может ещё не объявить совместимость. Каждую новую
  зависимость нужно проверять на поддержку 6.1 и Python 3.14
- **Версия PostgreSQL зафиксирована явно.** Переход на следующий мажорный релиз
  потребует отдельной процедуры миграции каталога данных, а не подмены тега образа
- **Lock-файл коммитится в репозиторий.** Без него весь смысл выбора uv теряется
- **SQLite не используется нигде**, включая тесты: его поведение отличается от
  PostgreSQL, и тесты на нём дают ложную уверенность

## Рассмотренные альтернативы

**Django 5.2 LTS.** Поддержка на несколько лет вперёд, обновляться не пришлось бы
долго. Отвергнут: API на два релиза старше, а проект прежде всего учебный —
изучать имеет смысл то, что актуально сейчас. Плата за это решение (более раннее
обязательное обновление) принята осознанно.

**psycopg 2.** Проверенная временем линейка, всё ещё поддерживается Django.
Отвергнута: развитие остановлено, новые возможности выходят только в третьей
версии, начинать новый проект на уходящей линейке смысла нет.

**Poetry.** Зрелый инструмент с lock-файлом, то есть основной критерий
удовлетворяет. Отвергнут в пользу uv из-за скорости и того, что uv покрывает
больше задач одним инструментом.

**pip-tools.** Минималистичный, даёт lock поверх обычного pip. Отвергнут:
требует ручной сборки окружения отдельными командами, тогда как uv решает это
целиком.

**SQLite вместо PostgreSQL.** Не требует Docker и настройки. Отвергнут: другой
набор типов, слабее ограничения целостности, иное поведение при параллельном
доступе. Разработка на одной СУБД и эксплуатация на другой — источник ошибок,
которые обнаруживаются только на проде.

**MySQL.** Отвергнут: PostgreSQL сильнее в том, что домену понадобится — типы
для работы с датами и интервалами, ограничения на уровне базы, оконные функции
для отчётности.
