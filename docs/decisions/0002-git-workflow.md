# ADR-0002. Процесс работы с Git и GitHub

- **Статус:** принято
- **Дата:** 2026-08-25

## Контекст

Проект ведётся одним разработчиком, но по правилам коммерческой разработки.
Процесс должен быть таким, чтобы его не пришлось менять при появлении второго
человека, и таким, чтобы он не обходился в момент усталости.

## Решение

### Модель ветвления — GitHub Flow

Одна долгоживущая ветка `main`, всегда в рабочем состоянии. Работа ведётся в
коротких ветках, которые вливаются через pull request и удаляются после слияния.

**Максимальный срок жизни ветки — 3 дня.** Не по эстетическим причинам: пока
ветка живёт, `main` уходит вперёд, и слияние превращается в разбор конфликтов
в коде, который автор уже забыл. Задача, не влезающая в 3 дня, нарезана плохо.

### Именование веток

```
<тип>/<номер-issue>-<краткий-слаг>
```

Примеры: `feat/42-membership-freeze`, `fix/57-booking-race`, `docs/12-glossary`.

Типы совпадают с типами коммитов — один словарь на всё. Номер issue в имени
превращает список веток в навигацию по трекеру.

### Сообщения коммитов — Conventional Commits

```
<тип>(<область>): <что сделает коммит, повелительное наклонение>

<тело: почему, а не что — «что» видно в диффе>

Refs: #42
```

Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `perf`, `chore`, `build`, `ci`.
Область — часть домена: `feat(memberships)`, `fix(visits)`.
Ломающее изменение помечается `!`: `feat(billing)!: ...`.

Соглашение выбрано не ради красоты, а ради машинной обработки: по такой истории
инструменты сами считают версию по semver, генерируют CHANGELOG и проверяют
формат в CI.

### Стратегия слияния — squash

В репозитории разрешён только squash-мерж, остальные способы отключены.
Ветки удаляются автоматически после слияния.

Каждый коммит в `main` — одна законченная задача. Это делает осмысленным
`git bisect`: поиск приводит к «фича X сломала», а не к промежуточному `wip`,
в точке которого код и не работал. Промежуточные коммиты не теряются — они
остаются на странице pull request.

Следствие: **заголовок PR становится сообщением коммита**, поэтому он обязан
соответствовать Conventional Commits.

### Защита `main`

Ruleset `protect main`, статус active, **список обхода пуст** — правила
действуют в том числе на владельца репозитория.

- обязательный pull request (required approvals = 0, иначе одиночка блокирует сам себя)
- запрет force-push
- запрет удаления ветки
- линейная история
- проверки CI — будут добавлены вместе с появлением CI

Обход выключен намеренно. Дисциплина, которую можно обойти усилием воли,
проигрывает усталости; правило не проигрывает. Когда обход действительно
понадобится, правило снимается осознанно — и эти тридцать секунд трения и есть
весь смысл.

### Планирование

- **Issue** — единица работы с проверяемым результатом. Формулировка, по которой
  нельзя однозначно сказать «сделано / не сделано», переписывается
- **Лейблы** — тип (`feat`, `bug`, `chore`, `docs`, `spike`), область домена,
  приоритет
- **Milestone** — спринт с датой
- **Доска:** Backlog → Ready → In progress → In review → Done.
  В `Ready` попадает только продуманное. **Лимит работ в процессе — 1**
- **Issue заводится не под каждый PR.** Issue — это прежде всего бэклог: способ
  не потерять то, что не делается прямо сейчас. Он нужен, если работа начнётся
  не сегодня, займёт больше дня, может быть отложена или содержит решение,
  которое надо зафиксировать до реализации. Мелкая работа, начатая и законченная
  за час, идёт сразу в PR. Когда issue есть — PR ссылается на него (`Closes #N`)
- PR больше ~400 строк диффа режется

## Последствия

- Прямой пуш в `main` невозможен, включая владельца репозитория
- Каждое изменение проходит через ветку, PR и саморевью
- История `main` линейна и читается как список изменений продукта
- Появление второго разработчика не требует менять процесс
- Плата: на каждое изменение накладываются расходы в виде ветки и PR

## Рассмотренные альтернативы

**git-flow** — постоянные `main` и `develop`, ветки `release/` и `hotfix/`.
Отвергнут: решает задачу параллельной поддержки нескольких выпущенных версий
коробочного продукта, которой здесь нет. Накладные расходы без выгоды.

**GitLab Flow** — GitHub Flow плюс ветки под окружения. Отвергнут пока:
окружение одно, фиксировать «что сейчас на проде» нечем и незачем.

**Trunk-based development** — пуш прямо в `main`, незаконченное за фича-флагами.
Отвергнут пока: требует зрелого CI и тестов, которых на старте нет. При этом
это естественное направление развития — ветки просто становятся короче.

**Merge commit / rebase and merge** — отвергнуты в пользу squash по причине,
описанной выше (читаемость `main` и осмысленность `git bisect`).

## Открытый вопрос

**Зачем нужен pull request разработчику, у которого нет ревьюера?**

Ни одно из правил выше не про «чтобы коллега посмотрел». Одиночке PR даёт другое:

**Смена угла обзора.** Диff, прочитанный в браузере, а не в редакторе, — это код
глазами читателя, а не автора. Другая вёрстка, другой контекст, нет привычного
окружения — и находится то, что замылилось за час написания. Дешёвых способов
поймать собственные ошибки немного, и этот работает только при смене обстановки.

**Место, куда встают проверки.** Тесты и линтер должны отрабатывать до попадания
в `main`, а не после. Без pull request нет ворот, и правило «`main` всегда
рабочий» остаётся пожеланием.

**Принудительная остановка.** Без PR задача перетекает в задачу, ветка живёт
неделю, и в какой-то момент уже не объяснить, что именно делалось. PR — точка,
где работа обязана быть законченной и осмысленной целиком.

**Контекст, которого нет в истории.** `git log` отвечает на «что». PR хранит
«почему»: описание, промежуточные коммиты, комментарии автора к своим строкам.
Через год при разборе странного места это единственный источник.

**Цена.** На мелких правках это накладные расходы: опечатка в README тоже
потребует ветку и pull request. Это плата за то, что правило действует всегда, а
не когда удобно.

> Статус этого раздела — **рабочая гипотеза**. Перечитать после пяти смерженных
> PR и записать, подтвердилась ли она на практике. Если нет — правило меняется.
