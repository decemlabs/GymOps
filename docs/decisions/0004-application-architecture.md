# ADR-0004. Распределение ответственности по слоям

- **Статус:** принято
- **Дата:** 2026-08-25

## Контекст

Согласно [ADR-0003](0003-product-boundaries.md), у системы будет два интерфейса
поверх одной бизнес-логики: веб-интерфейс персонала и REST API для клиентского
приложения. Логика, написанная внутри вьюх, окажется продублированной, а две
копии неизбежно разойдутся.

Решение принимается сейчас, до первого приложения, по простой причине: структура
первого приложения либо задаёт правило, либо навсегда закрепляет его отсутствие.
Разнести слои в проекте, где логика уже размазана по вьюхам, — это не рефакторинг,
а переписывание.

## Решение

### Слои и зоны ответственности

| Слой | Отвечает за | Не имеет права |
|---|---|---|
| **Модели** | Данные, инварианты, ограничения на уровне БД, простые вычисляемые свойства | Знать про HTTP; оркестрировать операции между несколькими моделями |
| **Менеджеры и QuerySet** | Переиспользуемые выборки: активные клиенты, действующие абонементы | Менять состояние |
| **Сервисы** | Операции, меняющие состояние: продать абонемент, отметить посещение. **Транзакции живут здесь** | Знать про запрос, ответ, сессию, текущего пользователя как объект HTTP |
| **Селекторы** | Сложные запросы на чтение и отчёты | Менять состояние |
| **Формы и сериализаторы** | Валидация формата входных данных, преобразование типов | Содержать бизнес-правила |
| **Вьюхи и представления API** | Разобрать запрос, вызвать сервис, сформировать ответ | Обращаться к ORM на запись; содержать бизнес-логику |
| **Фоновые задачи** | Расписание, повторные попытки, обработка сбоев | Содержать логику — только вызов сервиса |

### Правила, вытекающие из таблицы

1. **Вьюха не пишет в базу напрямую.** Любое изменение состояния идёт через сервис
2. **Сервис ничего не знает про HTTP.** Он принимает данные, а не запрос. Проверить
   легко: сервис должен вызываться из management-команды и из теста без подмены запроса
3. **Транзакция открывается в сервисе.** Не во вьюхе и не в модели: только сервис
   знает границы операции целиком
4. **Бизнес-правило живёт в одном месте.** Если оно проверяется и в форме, и в
   сервисе — источником истины является сервис, форма проверяет формат
5. **Сигналы применяются ограниченно и осознанно.** Это скрытый поток управления:
   код выполняется там, где его не видно при чтении. Допустимы для действительно
   побочных эффектов, запрещены для бизнес-логики

### Чего мы намеренно не делаем

Не вводятся репозитории, доменные сущности, отвязанные от ORM, классы сценариев
использования и разделение команд и запросов на уровне архитектуры.

Причина не в упрощении. Эти конструкции воюют с Django: здесь ORM **и есть** слой
доступа к данным, а Active Record — родная модель фреймворка. Абстракция поверх
ORM даёт много кода-переходника, ломает то, ради чего Django и берут (админку,
формы, готовые вьюхи), и приводит к тому, что изучается собственная прослойка, а
не фреймворк. Для проекта, одна из целей которого — глубокое освоение Django, это
прямое противоречие.

Граница проводится по принципу **«слой заводится тогда, когда без него больно»**.
Сервисы и селекторы этот порог проходят: без них операции, затрагивающие несколько
моделей, некуда положить. Репозитории — не проходят.

## Последствия

- Структура приложения включает `services.py` и `selectors.py` (или пакеты, когда
  файл разрастётся) с первого же приложения
- Тесты бизнес-логики пишутся на сервисы напрямую, без поднятия HTTP-слоя, — они
  быстрее и точнее
- Веб-интерфейс и API в v0.5 используют одни и те же сервисы. Второй интерфейс
  добавляет представления, но не бизнес-логику
- Плата: на простых операциях слой сервисов выглядит избыточным — вьюха из трёх
  строк вызывает сервис из четырёх. Это принимается сознательно: единообразие
  дороже экономии на простых случаях, потому что простые случаи со временем
  становятся сложными
- Правило требует дисциплины, а не инструмента: ничто в Django не помешает
  написать запрос в базу прямо во вьюхе. Соблюдение проверяется на ревью

## Рассмотренные альтернативы

**Классический Django-подход: толстые модели, тонкие вьюхи.** Идиоматично,
минимум кода, ровно то, что показано в документации. Отвергнут: некуда положить
операции, затрагивающие несколько моделей. Продажа абонемента создаёт и абонемент,
и платёж, и запись о продаже — в чьём методе этому жить? Любой ответ делает одну
модель осведомлённой о других и постепенно превращает её в тот же сервис, только
спрятанный.

**Логика во вьюхах.** Самое быстрое на старте. Отвергнут: при появлении API в
v0.5 вся логика будет продублирована, а тесты потребуют поднятия HTTP-слоя даже
для проверки арифметики.

**Чистая архитектура с репозиториями и доменными сущностями.** Максимальная
независимость от фреймворка, знакома по другим проектам. Отвергнута по причине,
описанной выше: цена в объёме кода и потеря родных возможностей Django не
окупаются, а учебная цель прямо страдает.
